## 1. 改动一：文件夹黑名单（隐藏 R-18 内容）

### 1.1 你要的行为

| 项 | 行为 |
|---|---|
| 过滤范围 | **包括「全部照片」视图**（默认首屏），以及文件夹 / 标签 / 收藏 / 未分组四种浏览模式 |
| 是否删除数据 | ❌ **绝不**。照片、缩略图、向量、人脸、phash 全部保留 |
| 是否取消索引 | ❌ **绝不**。照片依然在索引里，**并且依然可以被搜索到** |
| 搜索是否过滤 | ❌ **不过滤**（刻意如此，否则你将无法搜到 R-18 内容） |
| 何时仍会显示 | 你**主动在左侧点进**黑名单文件夹（或其子目录）时，正常显示 |
| 左侧树的数字 | 黑名单子树的照片数**不再计入其上级文件夹**，与右侧实际显示一致 |
| 怎么加入黑名单 | **右键文件夹 → 「不在主界面显示（不删除、仍可搜索）」** |

### 1.2 为什么用「路径」而不是「文件夹 id」

文件夹 id 在「从索引移除 → 重新导入」之后会变化，若存 id 会导致**黑名单静默失效**（NSFW 内容重新出现）。用绝对路径存储则不受影响，比较时做 Windows 大小写不敏感归一化。

### 1.3 存储位置

存在现成的通用键值表 `app_settings` 里，键名 **`folders.hiddenPaths`**，值是 JSON 数组，例如：

```json
["E:\\图\\[R-18&R-18G]"]
```

> **不需要数据库迁移** —— 这是刻意选择的方案（参照上游既有的 `faces.scanFolderIds` 写法）。
> 想手动清空黑名单，可以把这条 `app_settings` 记录删掉或设为 `[]`。

### 1.4 涉及文件与职责

| 文件 | 职责 |
|---|---|
| `src/utils/folder-exclusions.ts`（新增）| 纯函数：路径归一化、路径→id 解析、展开子树、判断"选中项是否在黑名单内" |
| `src/services/folder-exclusions.ts`（新增）| 存取层：读写 `app_settings`、按 id 反查路径后加入/移出黑名单 |
| `src/ipc/photos/handlers/shared.ts` | 新增 `HiddenFolderToggleSchema` 入参校验 |
| `src/ipc/photos/handlers/listing.ts` | **核心过滤**（3 处）+ 2 个新 IPC handler |
| `src/ipc/photos/index.ts` | 注册 `getHiddenFolders` / `setFolderHidden` |
| `src/components/Sidebar.tsx` | 右键菜单入口 + 状态加载 + 切换后刷新 |
| `src/localization/i18n.ts` | 中英文案 2 条 |

### 1.5 `listing.ts` 里的 3 处核心改动

**(a) `getFolders`（左侧树的数字）** —— 黑名单子树的照片数从其**所有祖先**里扣除；
黑名单文件夹自身及其子孙**保留真实计数**（这样你点进去看到的数字是对的）。
实现：从黑名单根开始向上遍历 `parentId`，逐级减去该子树的递归总数（带环保护）。

**(b) `listPhotos`（右侧网格的过滤）** ——

```ts
const folderRows = getAllFolderPathItems();
const hiddenPaths = getHiddenFolderPaths();
const excludedFolderIds = resolveExcludedFolderIds(folderRows);
const excludedIdSet = new Set(excludedFolderIds);

if (folderId) {
  const subtreeIds = getFolderSubtreeIds(folderRows, folderId);
  // 选中的文件夹本身在黑名单子树内 → 用户是主动点进来的 → 放行
  const visibleIds = excludedIdSet.has(folderId)
    ? subtreeIds
    : subtreeIds.filter((id) => !excludedIdSet.has(id));
  conditions.push(/* inArray(photos.folderId, visibleIds) ... */);
} else if (excludedFolderIds.length > 0) {
  // 「全部照片」等无文件夹条件的视图同样过滤
  conditions.push(
    or(isNull(photos.folderId), notInArray(photos.folderId, excludedFolderIds)) as SQL
  );
}
```

> ⚠️ **这里有一个必须保留的细节**：`or(isNull(photos.folderId), ...)`。
> SQL 里 `NULL NOT IN (...)` 的结果是 `NULL` 而不是 `true`，如果不包这一层，
> 所有 `folder_id` 为 NULL 的**孤儿照片**会从「全部照片」里凭空消失。

**(c) 计数缓存 key** —— 加入 `hiddenPaths.join("|")`。
否则切换黑名单后，界面上「共 N 张」的数字在 10 秒 TTL 内不会更新。

### 1.6 新增的两个 IPC 接口

| 接口 | 入参 | 作用 |
|---|---|---|
| `photos.getHiddenFolders` | 无 | 返回 `{ paths, resolvedFolderIds }` |
| `photos.setFolderHidden` | `{ folderId, hidden }` | 加入/移出黑名单，返回最新状态 |

> 设计说明：界面只传 **folderId**，**路径的解析放在主进程**（那里才有数据库），
> 避免把 Windows 路径语义泄漏到界面代码里。

## 2. 改动二：界面精简

### 2.1 一个集中的开关文件

**三项改动全部受 `src/config/private-build.ts` 控制。想恢复任何一项，把对应的值改成 `false` 即可：**

```ts
export const PRIVATE_BUILD = {
  hideDashboard: true,          // 改动二：隐藏「数据仪表盘」
  hideAlbums: true,             // 改动二：隐藏「相册」
  hideCull: true,               // 改动二：隐藏「选片」
  hideCloud: true,              // 改动二：隐藏云同步 / 云上传 / 分享
  hideUpdateBadge: true,        // 改动二：隐藏侧边栏底部"有更新"按钮
  hiddenSettingsRoutes: [       // 改动二：设置页里隐藏的路由
    "/settings/plugins",
    "/settings/wander",
    "/settings/sequences",
    "/settings/cloud-sync",
    "/settings/watermark",
    "/settings/update",
  ],
  hideExifFilter: true,         // 改动三：隐藏 EXIF 筛选面板 + 详情页 EXIF 区块
  disableExifExtraction: true,  // 改动三：停止导入时解析 EXIF + 停掉高级元数据后台补全
} as const;
```

> 改动一（文件夹黑名单）不在此开关里 —— 它是运行时功能，
> 通过右键文件夹菜单控制，黑名单内容存在数据库的 `app_settings` 表。

### 2.2 隐藏了什么、在哪隐藏的

| 隐藏对象 | 改的文件 | 具体位置 |
|---|---|---|
| 左侧导航「数据仪表盘」 | `Sidebar.tsx` | `{!PRIVATE_BUILD.hideDashboard && (<RailButton … />)}` |
| 左侧导航「相册」（含拖拽到侧边栏） | `Sidebar.tsx` | `{!PRIVATE_BUILD.hideAlbums && (…)}` |
| 左侧导航「选片」 | `Sidebar.tsx` | `{!PRIVATE_BUILD.hideCull && (…)}` |
| 侧边栏"有更新"按钮 | `Sidebar.tsx` | `{!PRIVATE_BUILD.hideUpdateBadge && updateAvailable && (…)}` |
| 命令面板（Ctrl+K）里的 3 个同名入口 | `SpotlightSearch.tsx` | `navigationItems` 数组末尾 `.filter((item) => !isSpotlightNavItemHidden(item.id))` |
| 选中照片后的「开始选片」/「上传到云」/「生成分享页」 | `SelectionActionBar.tsx` | 3 个菜单项的 `&&` 条件 + "更多操作"的显示条件 |
| 右键菜单里的「上传到云」/「生成分享页」 | `PhotoContextMenu.tsx` | 2 个菜单项的 `&&` 条件 |
| 设置页 6 个导航项 | `SettingsSidebar.tsx` | `NAV_ITEMS` 数组末尾 `.filter((item) => !isSettingsRouteHidden(item.to))` |

> **关键设计**：全部采用「**只隐藏入口，不删除代码**」。
> 路由文件、页面组件、后端逻辑、数据库表**一律保留**。
> 好处是：① 不会产生悬空路由引用（不会有编译错误）；② 随时可以改回 `false` 恢复。

### 2.3 为什么不用「删文件」的方式

如果删掉 `src/routes/dashboard.tsx` 等文件，TanStack Router 自动生成的 `routeTree.gen.ts` 会同步删除对应类型，于是所有指向该路由的 `navigate({ to: "/dashboard" })` 都会变成**类型错误**，需要连带清理首页的下钻返回逻辑等一串代码 —— 改动面大、易错、且不可逆。隐藏入口则完全避免这些问题。

### 2.4 设置页隐藏后的连带效果

- 设置页导航里「照片体验」「输出与同步」「更新与日志」这几个分组，如果项被删光，**分组标题会自动消失**（上游 `SettingsSidebar.tsx` 本身就有 `.filter(group => group.items.length > 0)`），无需额外改动。
- 设置项搜索（命令面板里搜设置）也自动不再显示这些项（因为它复用同一个 `NAV_ITEMS`）。

## 3. 改动三：去掉 EXIF 相关功能

### 3.1 你要的行为

| 项 | 行为 |
|---|---|
| 搜索栏的「EXIF 筛选」漏斗按钮 | ❌ **隐藏**（漏斗图标 + 整个筛选面板）|
| 面板内的筛选 | 日期范围 / 拍摄月份 / 拍摄时段 / 相机型号 / 镜头型号 / 创作者 / 高级摄影元数据 / ISO / 光圈 / 焦距 / 快门 —— **全部随之不可达** |
| 照片详情里的「EXIF 信息」区块 | ❌ **隐藏** |
| 导入新照片时的 EXIF 解析 | ❌ **停止**（不再写 `exif_data`）|
| 「高级摄影元数据」后台补全 | ❌ **停止**（不再调用 exiftool 反复读原图）|
| **已有 EXIF 数据** | ✅ **保留，不删除**（现有 37,735 行仍在库里）|
| 数据库表 / 迁移 | ✅ 完全不动 |

**顺带修掉了上游 BUG-2**（交接文档里的 P1 问题）：
上游对"没有 EXIF"的图片会为每张打 **2 条 `warn` 日志**，实测 1 小时 45 分产生 **13,686 条**，
5 MB 的日志文件只够记 4 分钟 —— 持续写盘、日志疯狂轮转，本身就在拖慢一切。
现在这两条日志改为 **`debug` 级别**，且关闭 EXIF 后根本不会产生。

### 3.2 为什么可以放心关掉（已逐项核实）

1. **你的图库几乎没有 EXIF**：79,777 张里 **42,042 张完全没有** EXIF（截图/下载图/插画），
   实测最高只有 `exif_data` 37,735 行。
2. **EXIF 筛选对你本来就是失效的**：面板里的「日期范围 / 拍摄月份 / 拍摄时段」也全部走
   `exif_data.dateTaken`，没有 EXIF 就筛不出任何结果。
3. **上游的「序列自动分组」刻意要求完整 EXIF**，代码注释原文：
   > *File timestamps can be rewritten during import/copy. Automatic grouping is intentionally EXIF-only to prevent false positives.*
   且要求"时间 + 设备 + phash"三者齐全（`capturedAt <= 0` 或 `!hasCompleteCaptureContext` 直接跳过）。
   **所以没有 EXIF 时序列本来就分不出组，关掉不会损失任何现有可用功能。**
4. **「漫游 / 时光胶囊」有兜底**：它用的是 `COALESCE(exif_data.dateTaken, photos.fileDate)`，
   没有 EXIF 会退回到文件时间，照常工作。
5. **「数据仪表盘」已经隐藏**（改动二），它才是 EXIF 统计的最大消费者。

## 4. 改动四：改名 AI Anime Image Manager + 独立图库（方案 B）

### 4.1 目标

与上游**彻底分叉**：本版以「AI Anime Image Manager」为独立软件存在，
拥有自己的数据目录，与已安装的上游原版**互不干扰**。

### 4.2 核心机制（必须理解，否则会以为"数据丢了"）

```
package.json 的 productName
   ↓ 决定
app.getPath("userData")   →  %APPDATA%\AI Anime Image Manager\
   ↓ 而 app-config.json 就存在 userData 里
src/utils/data-path.ts 读不到自定义 dataPath 时，就用 userData 当数据目录
   ↓
本版默认图库 = 自己的 userData 目录（全新空库）
```

**实测结果**：本版首次启动后自动建立了独立图库 `<图库>\`
（含 `data` / `models` / `thumbnails` / `vectors`），且**上游原库
`F:\AI Image Manager` 完全未被触碰**（最后写入时间不变）。

> ⚠️ 因为 `app-config.json` 存在 userData 里，**改名必然导致数据目录改变**。
> 换名字时不能只看界面，必须同时确认 dataPath。

## 5. 改动五：文件监听、开机补扫、批量打标签、标签性能

本节四项都是**为"直接往目录里存图 + 补漏角色标签"这个用法服务的**。
四项全部做过运行验证或数据验证，验证方式逐项写在下面。

### 5.1 chokidar 监听器：4,414 → 只监听根目录

**问题**：上游 `startWatching()` 给**每一个**文件夹都建监听器（本机实测 **4,414 个**），
而每个都带 `depth: 10` —— 父目录的监听器本就覆盖整棵子树，
于是同一个文件的新增事件会被多个祖先监听器重复上报，还占用大量目录句柄。

**改法**：新增 `getIndexedRootFolders()`（`src/services/indexer.ts`），
`startWatching()` 只对**树根**建监听器（受 `PRIVATE_BUILD.watchRootsOnly` 控制）。

> ⚠️ 判据是"父文件夹是否**真的存在于库中**"，不能简单用 `parent_id IS NULL` ——
> 该列虽声明了外键，历史上仍可能留下悬空值，那种子文件夹既不是根、也不会被任何祖先覆盖 → 会漏掉文件变更。
> 另加兜底：若一个根都找不到（如 parent 互相成环），退回监听全部文件夹。

**实测验证**（合成图库，真实运行）：

| 场景 | 结果 |
|---|---|
| 根目录 1 个 + 子目录 2 个（共 3 个文件夹）| 日志打印 `Watcher: Started watching folders` → **`count: 1`** ✅ |
| 两个独立根目录（共 4 个文件夹）| **`count: 2`** ✅ |
| 往**第 3 层**子目录写入文件（应用运行中）| ✅ 自动索引，且**正确归属到最深的子目录**（其 `photo_count` +1、`last_watcher_event_at` 有值）|

> **开发过程中此处曾引入一个真实 bug 并被运行验证抓到**：第一版祖先判断函数在
> `while` 循环走到 `parentId == null` 时直接 `return false`，导致子目录也被当成"根"
> → 监听器数量没降下来（日志显示 `count: 3`）。修好后 `count: 1`。

### 5.2 开机增量补扫（新增功能）

**问题**：chokidar 配了 `ignoreInitial: true` —— 监听器**启动时忽略已存在的文件**，
只报告启动后发生的变化。而代码里**没有任何开机补扫机制**（上游注释明确写着
*"never rescan every library on startup"*）。
本版用户习惯**直接往目录里存图**（不走导入对话框）→ **关机期间存的图永远不会入库**。

**改法**：新增 `scheduleStartupCatchUpScan()`（`src/services/import-queue.ts`），
在 `fileWatcher` 服务启动后延迟 25 秒，对每个树根调用现成的 `enqueueImport()` ——
复用既有的增量扫描、进度广播与后续 AI 处理。受 `PRIVATE_BUILD.startupCatchUpScan` 控制。
关机时会在 `suspendImportsForShutdown()` 里清掉定时器。

**实测验证**：

| 场景 | 结果 |
|---|---|
| 库里 4 张图全部位于关机状态（从未手动扫描）| ✅ 启动后自动全部入库 |
| 关机期间新增 2 张（根目录 1 张 + 第 3 层子目录 1 张）| ✅ 启动后全部补上（5 → 7 张）|
| 子目录记录 | ✅ 自动建 `folders` 行，`parent_id` 链正确（1→2→3），各层 `photo_count` 正确 |
| 68 张真实测试图（关机期间放入）| ✅ 启动后自动全部入库（75 张，缩略图齐备）|

### 5.3 批量打标签（新增功能，补漏核心）

**为什么需要**：WD14 tagger 只认得出约 **36–41%** 的图（原创角色 / 冷门角色没有训练标签，
因为 WD v3 丢弃了出现少于 600 张图的标签）。在 8 万张规模下逐个点开打标签不可行。

**改法**：

| 层 | 内容 |
|---|---|
| 后端 | `batchSetPhotoTag` / `batchRemovePhotoTag`（`src/ipc/photos/handlers/tags.ts`），语义与单张 `setPhotoTag` **完全一致**（`origin='manual'`、`isConfirmed/userConfirmed=true`）→ 后续任何 AI 重新打标签都不会覆盖它 |
| 实现 | **分块多行 UPSERT**（每块 200 行）：比逐张快，且避开 SQLite 单语句参数上限 |
| 前端 | 新增可复用组件 `src/components/BatchTagDialog.tsx`（搜索已有标签 / 直接新建并应用 / 支持中文输入法）|
| 入口 | 多选操作栏新增「批量打标签」按钮，接到 3 个路由：`index.tsx`、`albums.$albumId.tsx`、`people.$identityId.tsx` |

> ⚠️ 组件里**限制了渲染条数**（最多 200 条 + 提示继续输入缩小范围）——
> 做通用标签后标签总数会上万，一次性渲染上万个节点会卡死界面。

**实测验证**（在数据库副本上执行与 drizzle 生成 SQL 等价的语句）：

| 验证项 | 结果 |
|---|---|
| `photo_tags` 上是否存在 `(photo_id, tag_id)` 唯一约束 | ✅ 存在（`idx_photo_tag` UNIQUE INDEX），`ON CONFLICT` 目标合法 |
| 多行 UPSERT 插入 5 行 | ✅ 5 行 |
| 重复执行（幂等性）| ✅ 仍 5 行，不产生重复 |
| 字段语义 | ✅ `confidence=NULL, is_confirmed=1, origin='manual', user_confirmed=1`，与 `setPhotoTag` 一致 |
| 冲突时从 `auto` 升级为 `manual` | ✅ 正确升级 |
| 批量删除 | ✅ 行数正确 |
| 真实数据库 | ✅ 全程在**副本**上操作，真实库未被改动 |

### 5.4 修 `getTags` 性能（做通用标签前必做）

**问题**：`getTags`（`src/ipc/photos/handlers/tags.ts`）原本把**全表** `photo_tags`
拉进 JS 内存，为每个标签建 `Set<photoId>`，再对每个标签递归复制后代集合。
侧边栏每次刷新标签都会调用它。做通用标签后 `photo_tags` 会达到 80 万–320 万行 ——
实测足以冻住界面。

**改法**：把「自身 + 所有后代」的去重照片计数**下推到 SQLite**，
用一条递归 CTE（`closure(root, desc)`）+ `COUNT(DISTINCT photo_id)` 聚合，
只把 `#标签` 行（约 1 万行）返回给 JS。

**实测验证**（三重验证）：

1. **等价性（真实数据）**：用上游原库（142 标签 / 373,670 条配对）比对
   新 CTE 与旧算法的逐标签结果 → **142 个标签全部一致**
2. **等价性（drizzle 真实 SQL）**：用 `SQLiteSyncDialect` 生成 drizzle **实际会执行**的
   SQL 与参数，再在数据库副本上执行比对 → 无过滤分支与 `folder_id` 过滤分支**均完全一致**
3. **规模压力测试**（合成 1 万标签 / 296 万配对）：

| 实现 | 耗时 | 峰值内存 |
|---|---|---|
| 原 JS 算法 | 4,823 ms | **454.0 MB** |
| 新递归 CTE | 1,673 ms | **1.6 MB** |
| **改善** | **快 2.9×** | **省 276×** |

## 6. 改动六：WD14 动漫 tagger + 标签体系

### 6.1 为什么换掉上游的打标

上游用 SigLIP 对 **153 个硬编码英文概念**（`tag-suggester.ts`）做零样本匹配，词表是
**真人摄影概念**（猫咪 / 宠物 / 婴儿 / 花卉 / 晴朗 / 兔子…）。套在动漫插画上产出的是噪声 ——
实测本机库里出现过「猫咪 42,632 张」「婴儿 34,794 张」。

改用 **WD14 v3**（Danbooru 原生标签体系，10,861 个：通用 8,106 / 角色 2,751 / 分级 4）。

### 6.2 模型与预处理（照抄会失效，务必按此实现）

模型：`deepghs/wd14_tagger_with_embeddings` → `SmilingWolf/wd-vit-tagger-v3/model.onnx`
（在 SmilingWolf 原版基础上多一个 768 维特征输出）
放置位置：`<dataPath>/models/SmilingWolf/wd-vit-tagger-v3/`
配套 `selected_tags.csv`（词表，行序 = 输出下标）与 `zh_names.csv`（中文名映射）。

**用对照实验确定的三条硬性规格**（4 种组合 × 4 张图，只有一种能用）：

| 项 | 正确值 | 说明 |
|---|---|---|
| 输入布局 | **NHWC `[N,448,448,3]`** | ⚠️ `config.json` 写 `[3,448,448]` 是 timm 的约定，ONNX 导出时已转置 |
| 通道序 | **BGR** | 官方预处理 `image[:, :, ::-1]` |
| 数值范围 | **原始 0–255** | ⚠️ 用 `mean/std=0.5` 归一化会让模型**彻底失效**（4 张不同的图输出一模一样的垃圾）|
| 缩放 | 白底补成正方形 → 448×448（bicubic）| |

判定 BGR 的依据：模型认出 `112228640_p0.jpg` 是 `bronya_zaychik`（布洛妮娅，设定灰/银发），
BGR 给出 `grey_hair 0.94 / grey_eyes 0.96` ✅ 符合设定，RGB 给出 `red_hair 0.87` ❌ 不符。

### 6.3 涉及文件

| `src/services/ai/wd14-tagger-client.ts`（新增）| 单常驻 worker 客户端（比照 `text-worker-client` 的模式），含超时、崩溃重启、中止 |

### 6.4 实测数据（本机 131 张测试图 + 词表全量）

| 指标 | 结果 |
|---|---|
| 角色标签命中率 | **41%**（68 张普通图）／**10%**（51 张 NSFW 同人）|
| 通用标签命中率 | **100%**，平均 41 个/张 |
| 推理速度 | **0.23 秒/张**（单进程 CPU，读 512px 缩略图）|
| 全库推算 | 8 万张 CPU 约 **4 小时**（可中断续跑）|

> ⚠️ **NSFW 角色命中率明显偏低**是预期的：WD v3 训练时丢弃了出现 <600 张图的标签，
> 同人原创角色（OC）没有对应标签 —— 这正是「以图搜图 + 批量打标签」补漏的用途。

### 6.5 三种特征对「同一角色」的区分力（决定以图搜图用哪个）

方法：拿已确认同角色的图算两两余弦相似度，与 600 张随机图的 4000 对基线对比。

| 模型 | 维度 | 同角色平均 | 随机中位 | **差值** | 结论 |
|---|---|---|---|---|---|
| SFace（真人脸）| 128 | 0.3595 | 0.4076 | **−0.048** | ❌ 比随机还差（人脸聚类据此作废）|
| SigLIP（通用）| 768 | 0.7961 | 0.7401 | **+0.056** | ⚠️ 有信号但重叠大 |
| **WD14（动漫）** | 768 | **0.4424** | **0.2931** | **+0.149** | ✅ **约 2.7 倍** |

特征与标签是**同一次推理的两个输出**，所以采集它不增加任何推理成本。

### 6.6 标签体系（四项附加改动）

| 项 | 做法 |
|---|---|
| **通用标签中文化** | 用 `zh_names.csv`（23,799 条）把通用标签落库为 `中文 (english)`。<br>实测覆盖 **7,598 / 8,106 = 93.7%**；角色标签无中文来源，保持英文。<br>**英文留在括号里 → 中英文都能搜到。** |
| **二级类型目录** | `通用` 下按 13 个类型建二级目录。规则分类器的**加权覆盖**：<br>Top 100 最常见标签 **100%** 归类、Top 500 **99.2%**（长尾落"其他"）|
| **只显示有图的标签** | 侧边栏过滤 `photoCount > 0`。实测 10,933 个标签里只有 **551 个**有照片，其余 1 万多空标签不再渲染 |
| **标签黑名单** | 右键标签/分类 → 移入黑名单（含全部子孙），集中到面板**底部独立区域**（不随树滚动）。<br>左键点条目 = 按该标签筛选；右键 = 菜单里移出。**只影响显示，不删数据** |

### 6.7 两个容易踩的坑

1. **打标查找要用"英文基础名"**：中文化后库里的名字是 `中文 (english)`，
   而 worker 返回的是英文名 → `loadTagIdMap()` 与 `renameTag` 都必须按
   `baseNameOf()`（解析括号部分）建索引。已实测：**10,933 个标签的英文基础名 0 冲突**。
   角色名里的括号（`suzuran_(arknights)`）**括号前没有空格**，不会被误解析。
2. **空表在 LanceDB 里看不到**：`createEmptyTable` 建的表要等第一次写入才会提交到清单，
   用另一个连接 `tableNames()` 查不到是正常现象（日志里会有 `Created wd14_embeddings table`）。

## 7. 如何把改动移植到新版上游

1. 下载新版上游源码。
2. 把工作区里的 `需求分析/自用改动.patch` 用 `git apply` 打上去；
   或者按本文档的表格逐个文件手工重做。
3. **如果打补丁时报冲突**，说明上游改了同一处代码，需要人工合并 —— 重点检查：
   - `listing.ts` 的 `getFolders` / `listPhotos`（上游可能重构了过滤条件）
   - `tags.ts` 的 `getTags`（本版把计数下推成了递归 CTE）
   - `Sidebar.tsx` 的导航区与文件夹右键菜单
   - `SettingsSidebar.tsx` 的 `NAV_ITEMS` 数组
   - `indexer.ts` 的 `startWatching`（本版只对树根建监听器）
4. 五个新增文件（`private-build.ts`、`BatchTagDialog.tsx`、两个 `folder-exclusions.ts`、本文档）
   通常**直接放进去即可**，不受上游改动影响。

### ⚠️ 打补丁必须在关闭 `core.autocrlf` 的情况下执行

Windows 上 git 默认的 `core.autocrlf` 会把补丁里的 LF **改写成 CRLF**，
虽然 `git apply` 会返回成功，但打出来的文件行尾与工作区不一致。请用：

```bash
git -c core.autocrlf=false apply --whitespace=nowarn 自用改动.patch
```

> 这个坑在生成补丁时也踩过一次：Python 的 `Path.write_text()` 在 Windows 上
> 默认把 `\n` 转成 `\r\n`，导致**整份补丁每个 hunk 都 apply 失败**。
> 生成脚本已改为显式 `newline="\n"`。

**补丁已做过的验证**（每次重新生成都应重跑）：
1. 解压干净上游源码 → `git -c core.autocrlf=false apply` → **EXITCODE=0**
2. 与工作树**逐文件逐字节比对**（归一行尾后）→ 34/34 一致

> 建议：在 fork 后先 `git init` + 提交一次「上游原版」，再提交本次改动，
> 这样以后升级上游可以用 `git rebase` / `git merge` 而不是手工重放。

### ⚠️ 9.1 四个必须知道的坑（都实际踩过）

**坑 1：`ELECTRON_RUN_AS_NODE=1` 会让程序"静默秒退"**

如果环境变量 `ELECTRON_RUN_AS_NODE` 被设为 `1`，Electron 会以**纯 Node 模式**运行：
只把入口脚本当普通 JS 执行，**不创建窗口、不写日志、不报错，直接退出**。
现象极具迷惑性：`electron-forge start` 会打印「✔ Launched Electron app」然后就没了。

排查方法：`electron.exe --version`
- 正常 → 显示 **v41.1.1**
- 被污染 → 显示 **v24.14.0**（Node 的版本号）

> 上游 `forge.config.ts:467` 的 `RunAsNode: true` fuse 让 Electron 会响应这个变量。
> 启动脚本里已用 `set "ELECTRON_RUN_AS_NODE="` 清空它。

**坑 2：Electron 二进制从 GitHub 下载会卡死**

`npm ci` 的 postinstall 会从 `github.com/electron/electron/releases/download/...` 拉
约 120 MB 的 Electron 二进制，它会重定向到 `objects.githubusercontent.com`，
本机实测**会挂在 0 字节不动**（HEAD 请求能通，实际传输卡住）。

解法：设置镜像（已在启动脚本里写死）
```
ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/
```
实测镜像 **5.7 MB/s**，全量约 21 秒。加上包缓存复用，
`npm ci` 总耗时从「卡死几十分钟」变成 **60 秒**。

**坑 3：不要用重定向 stdio 的方式后台启动**

`electron-forge start` 是**交互式**命令（它读 stdin 以便响应 `rs` 重启主进程）。
用重定向管道/文件的方式在后台启动它，会引发两类问题：
- stdin 关闭 → forge 直接退出
- stdout 管道断开 → 程序的 `console.log` 撞上断管，抛 `EPIPE: broken pipe`，
  被 `bootstrap.ts` 当成致命错误弹「软件遇到严重错误」框

> **正确做法：在真实终端窗口里运行 `启动dev版.cmd`（双击）。**
> 若确实要无人值守地验证启动，用 `cmd /c "... > 文件 2>&1"` 做 OS 级文件重定向。

**坑 4：`.cmd` 启动脚本必须用 CRLF 换行 + 纯 ASCII**

第一版启动脚本用 LF 换行写的，双击后**窗口一闪就消失、什么都不做**。
原因是 **cmd.exe 需要 CRLF 换行**；用 LF 时它会把脚本读成碎片，报出一堆莫名其妙的错：

```
'de' is not recognized as an internal or external command
'PROJECT' is not recognized as an internal or external command
'注意:' is not recognized as an internal or external command
```

另外脚本里若含中文，在默认代码页（936/GBK）下也会被读成乱码。

**当前启动脚本的写法（已验证可用）：**
- **纯 ASCII 内容**（提示信息用英文），彻底规避代码页问题
- **CRLF 换行**（61 个 CRLF / 0 个裸 LF）
- 用 **`%~dp0`** 推导路径，因此**文件里不出现任何中文路径**
- 开头 `set "ELECTRON_RUN_AS_NODE="` 清空坑 1 的环境变量
